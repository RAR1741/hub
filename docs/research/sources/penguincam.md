## Purpose

PenguinCAM is a hosted web CAM tool that turns Onshape flat-plate and tube designs directly into CNC-router G-code, aimed at removing manual CAM software from an FRC team's manufacturing pipeline. A student selects a face in Onshape (or uploads a DXF), the tool auto-detects holes/pockets/perimeter/tube geometry, generates toolpaths with holding tabs and material-specific feeds/speeds, previews the cut in 3D, and downloads (or pushes to a team Google Drive) the finished `.nc`/G-code program. It is explicitly built to be multi-tenant: one hosted instance (`penguincam.popcornpenguins.com`) serves any FRC team that drops a `PenguinCAM-config.yaml` into their Onshape documents, with Team 6238's own settings as the universal fallback.

## Stack

- **Language:** Python (Flask) backend, vanilla JS frontend (no framework/build step).
- **Framework:** Flask (`frc_cam_gui_app.py`, ~2200 lines — routes, session/auth glue, DXF/G-code orchestration), served by Gunicorn in production (`Procfile`, `Dockerfile`) or Vercel's Python runtime (`app.py` — a thin Vercel entrypoint importing the Flask `app`, `vercel.json`).
- **Key libraries** (`requirements.txt`): `ezdxf` (DXF parsing/writing), `shapely` (polygon geometry — pocket/perimeter offsetting, island nesting), `google-auth`/`google-auth-oauthlib`/`google-api-python-client` (Google OAuth + Drive), `Flask-Limiter` (rate limiting), `requests`, `pyyaml` (team config), `gunicorn`.
- **Frontend:** `templates/wizard.html` + `static/wizard.js` — a single multi-step wizard (Setup → Parts → Layout → Preview) served three ways from one codebase: full-screen standalone (`/`, `/app`, DXF upload), and embedded in Onshape's right panel (`/onshape-panel`, `/onshape/element-panel`, live face-selection). `static/gcode_viewer.js` is a Three.js-based interactive 3D toolpath viewer with a cut-progress scrubber; `static/source_onshape.js` bridges Onshape's panel postMessage API.
- **G-code engine:** `frc_cam_postprocessor.py` (~5800 lines) — hole (helical entry + spiral clearing), pocket (contour offset + clearing), perimeter (tabbed offset cut), and tube-facing (two-phase flip) toolpath generation with per-material feeds/speeds and tool-radius compensation.
- **License:** MIT, Copyright (c) 2026 Popcorn Penguins, Inc. — `LICENSE.txt`.
- **Deployment:** Multi-target — `Dockerfile` (generic container, gunicorn), `Procfile` (Railway), `vercel.json` (Vercel serverless, `@vercel/python` builder). README documents Railway as the primary self-host path with GitHub auto-deploy on push to `main`; the hosted instance is the recommended path for other teams (no deployment at all).
- **Testing:** `tests/` — unit tests for config validation, harness classification/golden-file G-code, ring clearing, round perimeters, tube facing, session/job routes, and general utilities, run via `make test` (uses `uv` for dependency management per `README.md`).

## Auth & Roles

- **Two independent auth layers, one per entry surface:**
  - **Onshape OAuth 2.0** (`onshape_integration.py` — `OnshapeClient`, `OnshapeSessionManager`) gates the embedded-panel workflow (`/onshape/auth`, `/onshape/oauth/callback`, `/onshape/export-face`) — this is the trust boundary for the "click a face in Onshape" flow. Tokens are held server-side in an `OnshapeSessionManager` keyed by user id, with automatic refresh (`_ensure_valid_token`).
  - **Google OAuth 2.0** (`penguincam_auth.py` — `PenguinCAMAuth`, decorator `require_auth`) gates the standalone app (`/app`) when `AUTH_ENABLED=true`, restricted by `ALLOWED_DOMAINS`/`ALLOWED_EMAILS` env vars (`_check_authorization`) — this is also how a user grants Drive-upload scope (`https://www.googleapis.com/auth/drive`), since the same OAuth flow doubles as Drive authorization. Sessions last 30 days (`PERMANENT_SESSION_LIFETIME`), backed by `FLASK_SECRET_KEY` (falls back to a random per-process key with a startup warning if unset — breaks session persistence across redeploys).
- **Anonymous/public flow with a bot gate.** The no-login DXF-upload path is intentionally open (no Onshape or Google account required) but protected by Cloudflare Turnstile: the frontend solves a challenge, POSTs the token to `/session/verify` (`frc_cam_gui_app.py`), which mints `session['app_verified']` that the compute endpoints require. If `TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY` are unset, verification is bypassed with a loud startup warning (dev/test default, meant to be set on any public host).
- **No user-level roles/permissions model** — auth is binary (allowed-domain/email or not) per surface; there is a separate `require_admin()` gate (`frc_cam_gui_app.py`) protecting `/admin/metrics/summary` and `/admin/metrics/events`, but no broader admin/editor/viewer role system.
- **Rate limiting:** `Flask-Limiter`, default 200 requests/hour per IP (`limiter = Limiter(...)`), in-memory storage.

## Data Model

PenguinCAM has no persistent relational database — state is config files, session data, and generated files, not app-owned tables:

- **Team configuration** (`team_config.py` — `TeamConfig`) — loaded per-request from a `PenguinCAM-config.yaml` file discovered in the requesting user's Onshape documents (not stored locally), with every value optional and falling back to `TEAM_6238_DEFAULTS`. Supports a v1 (single implicit machine) and v2 (`machines: {machine_id: {...}}`, multiple named machines per team) schema, auto-upgraded from v1 on load. Config sections: `team` (number/name), `machine` (name/manufacturer/controller/dimensions/park_position/coolant/tube_work_coordinate_system), `machining` (z_reference, tabs, holes, default_tool), `tube_facing` (phase-1/phase-2 tool-edge and depth parameters), `materials` (per-material feeds/speeds/ramp/tab overrides), `integrations.google_drive` (enabled flag + folder id/URL).
- **Session state** — Flask server-side session (cookie-backed) holds Onshape/Google tokens, the active team config (cached, periodically refreshed — `_maybe_refresh_team_config`), and Turnstile verification flag. No user table; identity is whatever the OAuth provider asserts.
- **Ephemeral job files** — uploaded DXFs and generated G-code live in a temp directory (`/tmp` on serverless platforms, `tempfile.mkdtemp()` otherwise) behind a random-token download URL (`FileRegistry`-like class at the top of `frc_cam_gui_app.py` — `register_file`/`get_file`/`cleanup_old_files`, 1-hour expiry, periodic `cleanup_worker`).
- **Metrics store** (`metrics.py`) — a lightweight local event log (`_init_db`, `log_event`, `get_summary`, `get_events`) for admin-only usage/health metrics; not part of the manufacturing data model.
- **No parts/orders/roster/attendance data at all** — this tool is purely a CAD→G-code pipeline with no team-roster or purchasing concept.

## Features

- **Onshape one-click "Send to PenguinCAM"** — Right-panel Onshape extension; selecting a face and clicking through opens the wizard pre-loaded with that geometry. `docs/ONSHAPE_SETUP.md`, `frc_cam_gui_app.py` (`/onshape-panel`, `/onshape/element-panel`, `_serve_onshape_panel`), `static/source_onshape.js`.
- **Continuous face-selection while embedded** — Unlike a one-shot export, the Onshape-embedded wizard tracks the live selection so changing the selected face updates the loaded part without reopening the panel. `static/source_onshape.js`, `onshape_integration.py` (`auto_select_top_face`, `list_faces`).
- **Manual DXF upload** — Drag-and-drop DXF for offline work or non-Onshape CAD, served at `/` and `/app`. `frc_cam_gui_app.py` (`/process`, `/process-job`), `templates/wizard.html`.
- **Step wizard UI (Setup → Parts → Layout → Preview)** — One shared UI for both entry paths. `templates/wizard.html`, `static/wizard.js`.
- **Multi-part job layout** — Arrange several parts on one sheet for a single combined G-code program; the parts' bounding box becomes the stock, origin fixed at its lower-left (G54). Drag to move, drag-handle rotate with 45° snap, multi-select group move/rotate, mirror/flip, zoom. `static/wizard.js`, `frc_cam_gui_app.py` (`/process-job`).
- **Automatic hole detection** — All circular holes detected and cut to exact CAD dimensions (helical entry + spiral clearing), configurable minimum-millable-diameter multiplier vs. tool size. `frc_cam_postprocessor.py`, `team_config.py` (`hole_detection_tolerance`, `min_millable_hole_multiplier`).
- **Pocket recognition** — Auto-detects inner boundaries/islands (2.5D N-boundary polygon nesting) and generates offset clearing toolpaths, gated by a configurable area-vs-tool-diameter contour threshold so small pockets fully clear while large ones just get a perimeter pass. `frc_cam_postprocessor.py`, `team_config.py` (`machining.pockets.contour_threshold`).
- **Perimeter cutting with holding tabs** — Offset-outward perimeter cut with configurable tab count/width/height/spacing so cut parts don't fly loose. `frc_cam_postprocessor.py`, `team_config.py` (`machining.tabs.*`).
- **Aluminum tube support** — Tube-jig-based facing: mounts in a tubing jig (no X/Y zeroing needed), automatically squares the tube end, cuts to CAD length, mirrors the pattern across a mid-job flip using a two-phase roughing/finishing strategy on each face. `frc_cam_postprocessor.py` (tube-facing logic), `docs/TUBE_FACING_DESIGN.md`, `team_config.py` (`tube_facing.*`, `tube_work_coordinate_system`).
- **2D setup/orientation view** — Rotate the part in 90° increments (or free rotate in the layout step) before generating, origin fixed bottom-left. `static/wizard.js`.
- **3D toolpath preview with scrubber** — Three.js viewer animating the cutting tool along the generated path, with a scrubber to step through moves and see completed vs. upcoming cuts. `static/gcode_viewer.js`.
- **Split "Download / Send to Drive" save action** — One button, split by config: local download always available; "Send to Google Drive" gated by `integrations.google_drive.enabled` in the team config, remembers the user's last choice. `frc_cam_gui_app.py` (`/download/<token>`, `/drive/upload/<token>`, `/drive/status`), `google_drive_integration.py`.
- **Per-team multi-machine configuration via Onshape-hosted YAML** — Drop a `PenguinCAM-config.yaml` (v2 schema supports several named machines) into the team's Onshape documents; PenguinCAM auto-loads and merges it over Team 6238 defaults, no code change or redeploy needed. `team_config.py`, `PenguinCAM-config-template.yaml`, `frc_cam_gui_app.py` (`_load_team_config_into_session`, `_maybe_refresh_team_config`, `/config/refresh`).
- **Unit-flexible config values** — Any length-valued config field (machine dimensions, tab size, tool diameter, tube-facing offsets, etc.) accepts a bare number (inches) or a unit-suffixed string (`"4mm"`, `'0.25"'`, `"1/8"`), parsed identically server-side (`team_config.py: parse_length`) and client-side (`static/wizard.js`), so metric and imperial teams both write natural values.
- **Google Drive upload to a team Shared Drive** — Resolves a configured shared-drive name + folder path (or explicit folder ID/URL), uploads the finished G-code, returns a web link. `google_drive_integration.py` (`GoogleDriveUploader`).
- **Anonymous access with bot-gating** — The public DXF-upload flow works with no account, protected from abuse by a Cloudflare Turnstile challenge rather than a login wall. `frc_cam_gui_app.py` (`/session/verify`, `_verify_turnstile_token`).
- **Ephemeral, token-gated file downloads** — Generated files are registered under a random token and served once via `/download/<token>`, auto-expired after an hour by a background cleanup thread. `frc_cam_gui_app.py` (`FileRegistry`-style class, `cleanup_worker`).
- **Admin metrics dashboard endpoints** — Usage-summary and raw-event endpoints behind `require_admin()`. `frc_cam_gui_app.py` (`/admin/metrics/summary`, `/admin/metrics/events`), `metrics.py`.
- **Feeds & speeds reference tool** — A standalone calculator/reference page and API for material feed/speed presets, separate from the main job pipeline. `frc_cam_gui_app.py` (`/docs/feeds-speeds`, `/api/feeds-speeds`, `/api/feeds-speeds/presets`), `feeds_speeds.py`, `validate_feeds_speeds.py`, `static/docs/feeds-speeds.{html,css,js}`.
- **Debug/introspection routes** — Raw/processed DXF download and Onshape face-list debug endpoints for troubleshooting a specific job or Onshape document, gated behind the same session/auth as the main flow. `frc_cam_gui_app.py` (`/debug/download-dxf`, `/debug/download-raw-dxf`, `/debug/onshape/faces`, `/debug/session`).

## Integrations

- **Onshape REST API + OAuth 2.0** — `onshape_integration.py` (`OnshapeClient`, ~2200 lines): document/element listing, face/body detail queries, DXF export via Onshape's translation API (`start_dxf_translation`/`check_translation_status`/`download_translation_result`), multi-layer DXF export merging several depth-groups into one file with per-layer hatching (`export_multilayer_dxf`, `merge_dxfs_with_layers`), and reading the team's `PenguinCAM-config.yaml` straight out of the user's Onshape documents (`fetch_config_file`).
- **Google OAuth 2.0 / Drive API** — `penguincam_auth.py` (login/session), `google_drive_integration.py` (shared-drive + folder resolution, resumable upload via `MediaFileUpload`).
- **Cloudflare Turnstile** — bot-check for the anonymous upload flow (`frc_cam_gui_app.py`).
- **Vercel and Railway** — dual first-class deployment targets (`vercel.json`, `Procfile`, `docs/DEPLOYMENT_GUIDE.md`), auto-deploy from `main`.

## Notable Implementation Details

- **One codebase, three UI entry points.** `templates/wizard.html` is served unmodified at `/`, `/app`, and the Onshape-panel routes; the only difference is which source feeds it geometry (DXF upload vs. Onshape face-selection) and cookie `SameSite` policy (`EMBED_COOKIES=1` env var switches the session cookie to `SameSite=None; Secure` so it survives being loaded in Onshape's iframe).
- **Config-driven multi-tenancy with graceful degradation.** `TeamConfig._get()` walks a machine-specific override, then the built-in `TEAM_6238_DEFAULTS`, so a config file with just three lines (team number/name, machine name/controller, park position) is fully valid — every other value silently inherits Team 6238's tuned feeds/speeds/tab defaults. `is_material_complete()` and `get_material_preset()` explicitly track "using fallback" so a materially incomplete custom material still produces safe output rather than erroring.
- **Deliberately portable G-code by omission.** Several machine-config fields are *opt-in on purpose*, not defaulted, so their absence changes the emitted G-code dialect: no `park_position` → no `G53` machine-coordinate moves at all (needed for GRBL/Easel which reject G53); no `coolant` → no M7/M8/M9 codes; no `tube_work_coordinate_system` → tube jobs use G54 like flat work rather than assuming a fixed jig on G55+. This is called out explicitly in code comments and the YAML template (`team_config.py`, `PenguinCAM-config-template.yaml`).
- **Z=0 is the sacrifice board, not material top** — a deliberate coordinate convention (`docs/Z_COORDINATE_SYSTEM.md`) chosen so changing material thickness never requires recomputing Z offsets, at the cost of requiring a consistent guaranteed overcut (0.008" default) into the spoilboard on every job.
- **Corner feed-scaling is material-tuned, not physics-derived.** `team_config.py`'s `corner_min_feed_scale` documents in-code that aluminum (force-limited) gets an aggressive 0.4 slowdown at sharp pocket corners to protect the tool, while plywood/polycarbonate (heat-limited) use ~0.7 to avoid melting/rubbing from too slow a feed — a hand-tuned heuristic per material class, not a general model.
- **`SafeTestPostProcessor`** (`safe_test_mode.py`) is a test-only subclass of the real post-processor that force-disables the spindle (rewrites `M3`/`M03` to `M5`) and raises every Z height by 2" — a dry-run mode for verifying a program on a real machine without risk, run via `safe-test-mode.sh`/`safe_test_mode.py` rather than the web UI.
- **Anonymous flow's security model is explicit and narrow.** `frc_cam_gui_app.py` comments spell out that Turnstile — not login — is the anonymous flow's only gate, and that leaving `TURNSTILE_SITE_KEY`/`SECRET_KEY` unset is a documented, loudly-logged bypass meant only for local dev/tests, with an explicit warning to set both on any public host.
- **Actively developed, very recent.** This shallow clone's single visible commit ("Update documentation for anonymous usage") is dated 2026-08-21 — one day before this survey — and the README's "2.0 (in progress)" section describes an in-flight ground-up rework (the step-wizard architecture itself), so this is a live, fast-moving project rather than a stable/abandoned one. The `tests/` directory (unit + golden-file G-code tests, `make test`) indicates an unusually disciplined test posture for a small-team FRC tool.

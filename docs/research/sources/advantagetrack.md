## Purpose

AdvantageTrack is a self-hosted attendance system for a FIRST Robotics Competition team (FRC 6328, Mechanical Advantage), combining a touchscreen kiosk sign-in interface with automated presence detection of team members' phones and laptops on the shop's Wi-Fi network. A local Python server runs a full-screen web dashboard where students and mentors tap their name to sign in or out, while a background monitor thread flood-pings the local IP range and resolves responding hosts to MAC addresses, automatically opening and closing attendance "visits" for anyone who has opted in by registering a device. All configuration, roster data, and attendance records live in a Google Sheet that the server reads and writes continuously, so mentors and team leadership do their analysis and reporting inside the spreadsheet rather than in the app. Users are team members at the kiosk (sign in/out, register devices) plus an administrator who edits the Google Sheet config.

## Stack

- **Language:** Python 3.6+ (server), vanilla JavaScript ES modules (browser). No build step, no bundler, no transpilation.
- **Web framework:** CherryPy 18.7 (`web_server.py`) with `ws4py` 0.5.1 for WebSockets (`WebSocketPlugin`, `WebSocketTool`). Static files served by CherryPy's `staticfile`/`staticdir` tools. Port 8000, bound to `0.0.0.0`.
- **Database:** None locally — **Google Sheets is the database** (`google_interface.py`). The only on-disk persistence is a JSON config cache (`data/config_cache.json`) and downloaded background images (`data/backgrounds/`), both written by `main.py`/`google_interface.py`.
- **Key libraries:** `gspread` 5.4 (sheet read/write), `google-api-python-client` + `google-auth` (Drive file listing/download, service-account credentials), `Pillow` (background image downscaling and EXIF transpose), `netifaces` (local IP discovery), `pytz`, plus the `subprocess`-invoked external binaries `fping` and `arp`.
- **Frontend approach:** Single-page kiosk dashboard (`www/index.html`) driven almost entirely over one WebSocket (`www/static/modules/serverInterface.mjs`); state is held on `window` globals and propagated through custom DOM events (`configupdate`, `dataupdate`, `statusupdate`, `addaddressupdate`, `backgroundupdate`). Four ES modules under `www/static/modules/`. QR generation via a vendored `www/static/qrcode.js`. A second, server-rendered page (`www/add.html`) uses `$(...)` string placeholder substitution rather than a template engine.
- **License:** MIT, "Copyright (c) 2022 FRC 6328" — `LICENSE`.
- **Deployment/hosting:** Self-hosted only. No Docker, no Heroku, no CI, no service/systemd unit in the repo. `README.md` instructs cloning to a dedicated device on the team's LAN (Raspberry Pi recommended), installing deps in a virtualenv, hard-coding `SPREADSHEET_ID` in `main.py`, dropping service-account JSON at `data/google_credentials.json`, then running `python main.py` and opening a browser — optionally configuring the OS to auto-login, auto-start the script, and auto-open the browser for kiosk operation.

## Auth & Roles

**There is no user authentication or authorization of any kind.** The web server binds `0.0.0.0:8000` with no login, sessions, cookies, tokens, or CSRF protection (`web_server.py`), so anyone who can reach the host on the LAN can open the dashboard and sign in, sign out, or remove devices for any person on the roster. Identity is asserted by tapping a name in a list; the `/add` endpoint identifies the caller only by the MAC address behind their source IP.

The only credential in the system is the **Google service account** used server-side (`data/google_credentials.json`, loaded in `google_interface.py`; scopes `drive.readonly` and `spreadsheets.google.com/feeds`). Effective administration is therefore "whoever has edit access to the Google Sheet" — the roster, welcome message, IP range, and all timing behavior are edited there, not in the app (`GOOGLE.md`, README steps 2–3).

Role-like fields exist on people records but are not permission checks:
- `is_active` (`Config - People` column E) — inactive people are filtered out of the sign-in list but still appear in the manage-devices list (`www/static/modules/popupMenu.mjs`, `#updateTables`).
- `is_student` (column D) — parsed in `google_interface.py` and stored in the config cache, but never sent to the browser or used for any gating; it exists for spreadsheet-side analysis.
- `graduation_year` (column F) — same: parsed, stored, unused by app logic.

## Data Model

Five worksheets in one Google spreadsheet, discovered by exact title via `SheetType` in `google_interface.py`:

- **Config - General** (`C2:C13`) — 12 ordered scalar settings keyed positionally by `_CONFIG_KEYS`: `welcome_message`, `background_folder` (Drive folder ID), `ip_range_start`, `ip_range_end`, `ping_cycle_delay_secs`, `ping_timeout_secs`, `ping_backoff_length_secs`, `auto_grace_period_mins`, `auto_timeout_mins`, `auto_extension_mins`, `manual_timeout_hours`, `manual_extension_hours`.
- **Config - People** (`A:F`) — the roster: `id` (int, primary key), `first_name`, `last_name`, `is_student`, `is_active`, `graduation_year`.
- **Data - Devices** (`A:C`) — `person` (→ People.id), `mac` (normalized lowercase colon-separated), `last_seen` (date-granularity Unix timestamp). Many devices per person.
- **Data - Records** (`A2:E501`) — one row per visit: `person` (→ People.id), `start_time`, `end_time` (blank = currently signed in), `start_manual`, `end_manual` booleans distinguishing kiosk taps from automatic detection. Many records per person; at most one open record per person is assumed by `add_sign_in`.
- **Data - Status** (`A2:B2`) — server uptime heartbeat rows: server process start time, last-seen time.

Relationships are integer `person` id foreign keys with no enforcement. Rows are addressed by **spreadsheet row arithmetic** (`index + 2`), and new rows are always inserted at row 2 (newest-first), which is why the README warns that sample rows must not be deleted.

## Features

- **Kiosk dashboard / attendance home screen** — Full-screen sidebar UI with configurable welcome message (auto-sized by a font-shrink loop until it fits 15% of viewport height), sign-in button, "Who's Here?" list, manage-devices button, and status lights. — `www/index.html`, `www/static/index.js`, `www/static/index.css`
- **Manual sign-in** — Tap "Click to sign in", pick your name from an alphabetized 4-column grid; the server creates a new visit row (or reopens the person's existing open visit) in `Data - Records` with `start_manual = TRUE`. — `www/static/modules/popupMenu.mjs`, `www/static/modules/serverInterface.mjs`, `web_server.py` (`sign_in` query), `google_interface.py` (`add_sign_in`)
- **"Thank you" confirmation screen** — After signing in, a sliding panel shows "Thank you! Please sign out when you leave." and auto-dismisses after 3 seconds. — `www/index.html`, `www/static/modules/popupMenu.mjs` (`#thanksTimeoutLengthMs`)
- **Manual sign-out from "Who's Here?"** — Tap your own name in the live present-people list to close all your open visits with `end_manual = TRUE`. — `www/static/modules/hereNow.mjs`, `web_server.py` (`sign_out` query), `google_interface.py` (`add_sign_out`)
- **Live "Who's Here?" board** — Real-time 3-column list of everyone with an open visit, sorted manual-first then alphabetically; automatically-detected people are rendered underlined/styled distinctly (`.auto`) with an on-screen legend explaining they'll be signed out automatically. — `www/static/modules/hereNow.mjs`, `www/index.html`, `www/static/index.css`
- **Sign-in list filtering** — People already signed in manually are hidden from the sign-in list, and inactive roster members are excluded entirely. — `www/static/modules/popupMenu.mjs` (`#updateTables`)
- **Automatic sign-in via network presence** — A monitor thread flood-pings the configured IP range, resolves each responder's MAC via `arp`, matches against registered devices, and opens a visit (`start_manual = FALSE`) for the owner. — `monitor.py`, `arp.py`
- **Automatic sign-out on device disappearance** — When a person's devices haven't been seen for `auto_timeout_mins`, their visit is closed with an end time backdated to last-seen plus `auto_extension_mins` (so the recorded departure approximates when they actually left, not when the timeout fired). — `monitor.py`
- **Manual-sign-out grace period** — After someone manually signs out, automatic detection will not re-sign them in for `auto_grace_period_mins`, preventing a person walking out the door from being immediately re-detected. — `monitor.py`
- **Forgotten manual sign-out cleanup** — Manual visits still open after `manual_timeout_hours` are auto-closed with the end time set to start plus `manual_extension_hours`, so a forgotten sign-out doesn't record an all-night visit. — `monitor.py`
- **Device management panel** — Pick any person (including inactive ones) to see their registered devices with MAC address and last-seen date, a registration how-to, and a per-device Remove link. — `www/static/modules/popupMenu.mjs` (`#updateDeviceDetails`), `www/index.html`
- **Device registration pairing flow (`/add`)** — Selecting a person on the kiosk arms an "auto add" slot on the server; the user then browses to `/add` from the device they want registered, and the server resolves their source IP to a MAC via `arp` and writes it to `Data - Devices` for the armed person. Valid for 10 minutes. — `web_server.py` (`Root.add`, `auto_add` query, `_AUTO_ADD_TIMEOUT_SECS`), `arp.py`, `google_interface.py` (`add_device`), `www/add.html`
- **Randomized-MAC detection and user guidance** — `/add` rejects registration if the device presents a locally-administered/randomized MAC, showing instructions to "Forget This Network" and disable "Private Wi-Fi Address" / "Randomized MAC"; the kiosk panel shows the same per-OS steps. — `arp.py` (`random_mac_address_pattern`), `www/add.html` (`FAILURE-RANDOM`), `www/index.html`
- **Registration result page with distinct error states** — `/add` returns one of five outcomes rendered by CSS class on `<body>`: `SUCCESS`, `FAILURE-GETMAC` (couldn't read MAC), `FAILURE-RANDOM`, `FAILURE-PERSON` (no armed person / expired), `FAILURE-GOOGLE` (sheet write failed), always echoing the detected MAC where known. — `web_server.py`, `www/add.html`, `www/static/add.css`
- **QR code for device registration** — A 512×512 QR code of the `/add` URL is generated in-browser so users can scan instead of typing; it regenerates whenever the server's detected LAN IP changes. — `www/static/modules/popupMenu.mjs` (`#updateAddAddress`), `www/static/qrcode.js`, `web_server.py` (`add_address`, `_monitor_ip`)
- **Device removal** — Remove link next to each registered device deletes the matching row(s) from `Data - Devices`, opting that device out of automatic tracking. — `www/static/modules/popupMenu.mjs`, `web_server.py` (`remove_device` query), `google_interface.py` (`remove_device`)
- **Device last-seen tracking** — Registered devices seen on the network get a day-granularity `last_seen` stamp written to the sheet (at most one write per device per day), surfaced in the device list so members can spot devices whose MAC has been reset by the OS. — `monitor.py`, `google_interface.py` (`update_device_last_seen`)
- **Three-light system health indicator** — Server / Monitor / Google lights each show disconnected, warning, or connected, with documented semantics (e.g. Monitor warning = zero devices visible, possible network problem; Google warning = unexpected sheet data). — `main.py` (comment block defining the states), `web_server.py`, `www/static/index.js` (`updateStatusLights`), `util.py` (`ConnectionStatus`)
- **Connectivity warning banners and input lockout** — When the WebSocket or Google connection is down, "Cannot connect to server/Google" banners appear and the name tables are visually disabled and stop accepting taps, so users can't make sign-ins that would be silently lost. — `www/static/modules/hereNow.mjs`, `www/static/modules/popupMenu.mjs`, `www/index.html`
- **Automatic WebSocket reconnection** — The client retries the socket every 3 seconds after a close and resets all statuses to disconnected in the meantime. — `www/static/modules/serverInterface.mjs`
- **Scrolling background photo wall** — Team photos from a Google Drive folder scroll continuously across a canvas behind the UI, with a separately-rendered blurred copy composited behind the sidebar; falls back to three bundled defaults until the Drive sync completes. — `www/static/modules/backgrounds.mjs`, `google_interface.py` (`_update_backgrounds`), `web_server.py` (`backgrounds` query, `/backgrounds/user` and `/backgrounds/default` static mounts), `default_backgrounds/`
- **Spreadsheet-driven configuration (admin)** — All admin settings — welcome message, roster, IP scan range, ping timing, and every grace/timeout/extension window — are edited in the Google Sheet and picked up by the running server within a minute, with no restart or app-side admin UI. — `google_interface.py` (`_CONFIG_KEYS`, `_update_config`, `_cache_thread`), `main.py` (`update_config_cache`)
- **Server uptime/heartbeat log (admin)** — Every minute the server writes the current time against its process start time in `Data - Status`, inserting a new row per server run, giving admins a record of server sessions and downtime. — `google_interface.py` (`_update_status`)
- **Offline config resilience** — The config cache is written to `data/config_cache.json` and reloaded at startup, so the kiosk can render the roster and welcome message even if Google is unreachable at boot. — `main.py`, `google_interface.py`
- **Unsupported-browser alert** — If the ES-module entry point never runs, a plain-script fallback alerts that the browser may be too old. — `www/static/unsupportedAlert.js`, `www/static/index.js` (`window.mainAlive`)
- **Reports and analytics (external)** — The app itself ships no reports, charts, or export endpoints; hour totals and attendance analysis are formulas in the shared Google Sheet template linked from the README, and "export" is simply the spreadsheet's own download features. — `README.md`

## Integrations

- **Google Sheets** — Primary datastore for config, roster, devices, records, and status, via `gspread` with service-account credentials; sheets located by title, rows addressed by index. — `google_interface.py`, `GOOGLE.md`, `README.md`
- **Google Drive** — Lists and downloads JPEG/PNG background images from a configured folder ID via `google-api-python-client` (`files().list` with `supportsAllDrives`, chunked `MediaIoBaseDownload`), then downscales with Pillow. — `google_interface.py` (`_update_backgrounds`)
- **Google Cloud service account** — Setup instructions for enabling the Drive and Sheets APIs and minting a JSON key; the sheet must be shared with the service-account email (edit) and the background folder (view). — `GOOGLE.md`, `README.md`
- **`fping` (network presence detection)** — External binary invoked with `subprocess.Popen(["fping", "-C", "1", "-r", "0", "-t", <timeout_ms>, "-q", ...])`; results parsed from stderr. Per-OS install instructions provided. — `monitor.py`, `FPING.md`
- **`arp` (IP → MAC resolution)** — External binary invoked per responding IP, with separate output-parsing branches for Linux, macOS (Darwin), and Windows, followed by MAC normalization and regex validation. — `arp.py`
- **`netifaces` (host IP discovery)** — Polls interfaces every 5 seconds to find the server's non-loopback IPv4 address so the `/add` URL and QR code stay correct across DHCP changes. — `web_server.py` (`_monitor_ip`)
- **`qrcode.js` (vendored)** — Third-party client-side QR generator bundled into the repo; no CDN dependency. — `www/static/qrcode.js`
- **Barcode scanners, RFID, Slack, email, SMS, push notifications** — none. There is no messaging, notification, or badge-scanning integration anywhere in the codebase; the QR code is displayed for humans to scan with their own phone camera, not read by the app.

## Notable Implementation Details

- **Threaded, callback-wired architecture with no framework glue.** `main.py` instantiates three components and connects them purely with lambdas — `GoogleInterface` (Google I/O + polling), `WebServer` (HTTP/WebSocket + IP monitor), `Monitor` (network scanning) — each spawning daemon threads; the main thread just `time.sleep(1)` forever. There is no async, no task queue, no scheduler library, and no shared lock: the config and data caches are plain dicts read via getter lambdas from multiple threads.
- **Several classes declare mutable state as class attributes** rather than instance attributes (e.g. `_connection_status`, `_last_seen_ips` in `monitor.py`; `_auto_add_person` in `web_server.py`), and `Root`/`WebSocketHandler` reach the parent through a class-level `_parent` set by `set_parent`. This works because exactly one instance of each exists, but is worth understanding before restructuring.
- **Wall-clock second-of-minute scheduling.** `google_interface._cache_thread` sleeps until the next second-of-minute in a fixed list rather than using intervals: config at :30/:60, data at :10/:20/:30/:40/:50/:60, status at :60. Background sync piggybacks on the config refresh (deliberately skipped at startup because it can be slow).
- **Row-index arithmetic against the live sheet.** Every write re-reads the relevant sheet first, computes `index + 2` row numbers from the in-memory list, then inserts at row 2 or updates a cell range. Because indexes are derived from returned rows, the README's warning not to delete the template's sample rows is a hard correctness requirement, and concurrent edits by a human in the sheet can misalign writes.
- **Bounded record window.** Only the newest 500 records are ever read (`_RECENT_RECORDS`), which bounds API cost but also means open visits older than 500 records are invisible to the sign-out and grace-period logic.
- **Timestamps are naive Unix seconds and the timezone must match.** The README requires the Google Sheet's timezone to equal the local server's; `update_device_last_seen` truncates to local midnight via `datetime.combine(today, time.min)`. There is no UTC normalization.
- **Per-IP ping backoff.** IPs seen within `ping_backoff_length_secs` are excluded from the next flood ping, shrinking each scan on a busy network. A side effect encoded in the status logic: "zero devices found" only raises a warning when nothing was skipped either.
- **Backdated sign-out times.** Both automatic and manual timeouts write an *estimated* departure time (last-seen + `auto_extension_mins`, or start + `manual_extension_hours`) rather than the detection time. Auto-timeout people are intentionally **not** removed from the in-memory `_last_seen_people` map so the sign-out request repeats on the next cycle if the Google write fails.
- **Google state is authoritative for the monitor.** Each cycle reconciles the local `_last_seen_people` map against open non-manual records fetched from the sheet, so a server restart or an out-of-band sheet edit re-syncs rather than double-signing people in.
- **Pairing security model.** `/add` trusts `cherrypy.request.remote.ip` and the ARP table; the armed person is a single global slot with a 10-minute expiry (the newest commit, "Add timeout for auto add logic"). Two people registering at once would collide on that slot. Note also that `is_random`/`google_success` in `Root.add` are referenced in the response-building branch after being assigned only inside the earlier conditional.
- **WebSocket-first protocol, no REST.** All reads and writes except `/add` and static files flow through one socket with a `{query, data}` JSON envelope; on connect the server pushes six messages (`monitor_status`, `google_status`, `add_address`, `config`, `data`, `backgrounds`), and updates are broadcast to every connected client via `cherrypy.engine.publish("websocket-broadcast", ...)`. The client uses plain `ws://`, so HTTPS/WSS is not supported as written.
- **Cache-diff broadcasting.** `main.py` compares new config/data against the previous dict and only pushes to the web server on change, avoiding constant redraws in browsers.
- **Backgrounds are content-addressed by Drive file ID.** Local filenames are `<driveFileId>.<jpeg|png>`, so syncing is a plain set difference between the local folder listing and the Drive listing; images are resized to 1200px height with EXIF orientation applied before caching, and the file list is shuffled server-side on each `backgrounds` message.
- **Canvas-rendered background at animation-frame rate.** `backgrounds.mjs` fully re-initializes both canvases (resetting `width`/`height` and re-scaling for `devicePixelRatio`) and redraws every `requestAnimationFrame`, duplicating the image array enough times to cover the viewport and deriving scroll offset from wall-clock time modulo a wrap period — a continuous CPU/GPU load appropriate to a dedicated always-on kiosk.
- **Hardware and network assumptions.** Requires a network that permits ICMP echo to the whole configured range, devices with MAC randomization disabled *for that network only*, `fping` and `arp` on `PATH`, and an always-on host on the same L2 segment as the tracked devices (ARP resolution only works within the broadcast domain). A dedicated always-logged-in machine with a browser in kiosk mode is the intended deployment.
- **Configuration is partly source-code.** `SPREADSHEET_ID` and `ENABLE_MONITOR` (a testing switch that disables all network scanning) are constants edited in `main.py`; the port 8000, 500-record window, 1200px background height, 5-second IP poll, and 10-minute pairing timeout are constants in their respective modules. There is no `.env`, config file, or CLI argument parsing.
- **Error handling is broad and status-driven.** Most Google and monitor operations are wrapped in bare `except:` blocks that log a message and downgrade the corresponding status light rather than raising, which keeps the kiosk running but means the light semantics documented in `main.py` are the primary diagnostic surface, alongside stdout logging via `util.log`.

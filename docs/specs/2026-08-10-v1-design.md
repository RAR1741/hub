## 1. Scope

**v1 is attendance + roster, nothing else.** The parts, comms, events, and planning domains are all deferred to issues.

In scope (catalog § in parens):

1. Name-tap kiosk sign-in/out (1.1, 1.2)
2. Live "who's here" board (1.4)
3. Hours totals, leaderboard, per-member detail (1.5)
4. Build-day attendance calendar with required/optional days and excusals, anchored on Google Calendar meetings (1.6, 5.2)
5. Time-clock periods / seasons (1.8)
6. Session editing + suspect-session review (1.9) — *no audit/versioning infra; that was de-scoped in §6*
7. Member roster with profiles (2.1)
8. Teams/subteams tree with memberships (2.2)
9. Five fixed roles with server-enforced guest read-only mode (2.3, §7)
10. Split-audience auth: student ID + mentor Google OAuth, account-request queue, first-user-admin bootstrap (2.4)

Explicitly out of v1 (with issue links): Wi-Fi presence ([#1](https://github.com/RAR1741/hub/issues/1)), offsite-hours verification ([#2](https://github.com/RAR1741/hub/issues/2)), meeting-end auto-close ([#3](https://github.com/RAR1741/hub/issues/3)), relationships ([#4](https://github.com/RAR1741/hub/issues/4)), badges ([#5](https://github.com/RAR1741/hub/issues/5)), RFID/barcode ([#6](https://github.com/RAR1741/hub/issues/6)), granular RBAC ([#7](https://github.com/RAR1741/hub/issues/7)), all of parts/purchasing/inventory/printing ([#8](https://github.com/RAR1741/hub/issues/8)–[#16](https://github.com/RAR1741/hub/issues/16)), all email ([#17](https://github.com/RAR1741/hub/issues/17), [#21](https://github.com/RAR1741/hub/issues/21)), announcements ([#18](https://github.com/RAR1741/hub/issues/18)), Slack ([#19](https://github.com/RAR1741/hub/issues/19) — first post-v1 item), Q&A ([#20](https://github.com/RAR1741/hub/issues/20)), suggestion box ([#22](https://github.com/RAR1741/hub/issues/22)), events with check-ins ([#23](https://github.com/RAR1741/hub/issues/23)), task boards ([#24](https://github.com/RAR1741/hub/issues/24)), dashboards ([#25](https://github.com/RAR1741/hub/issues/25)), platform patterns ([#26](https://github.com/RAR1741/hub/issues/26)).

**No email anywhere in v1.** Consequence checked feature-by-feature: the account-request queue is reviewed in-app (admins see a pending list); approvals/denials surface in the app, not by email. And because mentors use Google OAuth and students use ID-number sign-in, **v1 has no passwords at all — so no reset flow is needed**. That's a feature of the design, not a gap.

## 3. Auth & identity

### 3.1 The person/user split
`person` is the roster entity (every member, whether or not they can log in). Authentication identities *link to* a person:

- `person.auth_user_id` (nullable, unique) → Supabase Auth user, for mentors/admins today and **for students when they later get Google OAuth** — satisfying the future-proofing requirement: adding OAuth to a student is just filling in this column; their punches, hours, and history all hang off `person.id` and never move.
- `person.student_id_number` (nullable, unique, **arbitrary string** per §8 answer 3) → what a student types to sign in; can be a phone number, school ID, or any other string the team assigns.

### 3.2 Mentor sign-in (Supabase Auth)
Google OAuth via Supabase Auth. An **allowlist check** (Den's model) runs server-side after callback: if the Google email matches no person with role mentor/admin/captain and isn't in the pending-approval path, the session is downgraded to guest. No self-serve mentor creation.

### 3.3 Student sign-in (app-issued session)
Supabase Auth has no "type an ID number" flow, so students get an **app-managed session**: a server route validates the ID against `person.student_id_number`, then issues our own signed, HTTP-only session cookie (JWT signed with a server secret; payload = person id + role + expiry). Deliberately low-friction and low-trust — same posture the review accepted for the kiosk. Design consequences:

- Two session types (Supabase session for OAuth users, app JWT for students) are normalized by one server-side `getViewer()` helper that returns `{ person, role }` for every request. All authorization flows through it.
- We do **not** create synthetic Supabase Auth users for students; that path makes the later OAuth link-up messier, not easier.

### 3.4 Account-request queue & bootstrap
- "New student? Request an account" form (name, grad year, optional email) → `account_request` row → admin reviews in-app, approving creates/links a `person` and assigns the student ID number.
- **First-user bootstrap** (GP's trick): the first successful Google OAuth sign-in when zero admins exist becomes admin automatically. After that, roles are assigned by admins only.

### 3.5 Roles & the authorization seam
Five fixed roles on `person.role`: `admin`, `mentor`, `captain`, `student`, `guest` (guest = the unauthenticated default; not stored). Enforcement:

- **All reads/writes go through Next.js server routes** (route handlers / server actions) using the Supabase service key; role checks happen in app code via `getViewer()`. Guests get real read-only responses server-side (Den's model), not hidden UI.
- **RLS stays enabled on every table** with default-deny and **zero policies** — with who's-here polling through a server route (per §8 answer 4), there is no client-side data path at all in v1. Everything is service-key-only.
- This is the seam, decided once: **authz in app code; RLS as the locked door.** (The Realtime upgrade, [#27](https://github.com/RAR1741/hub/issues/27), would add exactly one narrow anonymous-SELECT policy for the who's-here columns.)

### 3.6 Kiosk trust model
The kiosk is a public cloud page, unlike AdvantageTrack's LAN-only server, so a fully open clock-in endpoint would accept writes from anywhere on the internet. v1 uses a **registered kiosk device**: an admin generates a kiosk token in settings; entering it once on the shop tablet stores it (long-lived cookie); the kiosk clock-in/out endpoints require it. Within the kiosk, identity is name-tap — spoofable by people physically present, which the review accepted. (Escalation paths — barcode/RFID — are [#6](https://github.com/RAR1741/hub/issues/6).)

## 4. Data model

All timestamps `timestamptz` (UTC). Postgres, UUID PKs.

```
person            id, first_name, last_name, display_name?, role (enum), grad_year?,
                  email?, phone?, shirt_size?, dietary_restrictions?, bio?, avatar_path?,
                  is_active (bool), student_id_number? (unique), auth_user_id? (unique → auth.users)
account_request   id, first_name, last_name, grad_year?, email?, status (pending/approved/denied),
                  reviewed_by? (→person), reviewed_at?, created_at
team              id, name, parent_team_id? (→team), description?, join_mode
                  (admin_only / open / requires_approval)
team_membership   (person_id, team_id) PK, is_manager (bool), joined_at
membership_application  id, person_id, team_id, message?, status, reviewed_by?, reviewed_at?
period            id, name ("2027 Build Season"), starts_on, ends_on, is_active
session           id, person_id, period_id, time_in, time_out?, source (kiosk/manual/admin),
                  note?, excluded_from_totals (bool), edited_by? (→person), edited_at?
meeting           id, gcal_event_id (unique), title, starts_at, ends_at, synced_at
build_day         date PK, kind (required/optional), source (gcal/manual), meeting_id?
excusal           (person_id, date) PK, note?, created_by (→person)
kiosk_device      id, name, token_hash, created_by, last_seen_at?
app_setting       key PK, value (jsonb)   -- team timezone, gcal calendar id, etc.
```

Notes:
- `session.time_out IS NULL` = currently signed in (AT/CH convention). A partial unique index enforces **one open session per person** (Den's invariant).
- `build_day.kind` precedence is explicit and stored, not derived at query time — CH's derived-CASE approach is the main thing its own code warns us off of. Sync marks meeting days; admins can override any date manually (`source` records which won).
- `excluded_from_totals` + `edited_by/edited_at` on sessions is the entire "audit" story in v1 — who last touched it, and whether it counts. No versioning tables.
- Attendance status per (person, build_day) is **computed**: present if any non-excluded session overlaps the date; else excused if an excusal row exists; else absent (penalized only when `kind = required`). Excusals shrink the denominator (CH's math).

### Timezone policy (the paragraph every surveyed codebase needed)
Store UTC everywhere. One team timezone in `app_setting` (default `America/Indiana/Indianapolis`). All day-boundary logic — "which date does this session belong to", build-day matching, the nightly sweep — converts through that single setting on the server. No browser-offset arithmetic, no naive timestamps.

## 5. Integrations & scheduled jobs

**Google Calendar (read-only).** A Google service account with read access to the team calendar. A pg_cron job (hourly) calls a Next.js sync endpoint (or Edge Function) that upserts events into `meeting` and marks their dates as build days (default `required`; admins flip to `optional` in the UI). Manual build-day creation also exists, so v1 works even before the calendar is connected.

**Nightly sweep (pg_cron, ~3:30am team time, pure SQL).** Closes any session still open from a previous day: `time_out = time_in + N hours` (setting, default 4h), flags it `source = 'admin'`-editable and lists it on the flagged screen. This is the GP-style heal; Den's smarter meeting-end backdating is [#3](https://github.com/RAR1741/hub/issues/3).

**Flagged-sessions screen feeds** (computed, not stored): sessions > max-shift-hours setting, sessions auto-closed by the sweep, overlapping sessions for one person.

## 7. Testing & quality

- Vitest for unit tests on the pure logic (attendance computation, build-day precedence, hours math, timezone/day-boundary edges — the places CH/AT got burned).
- Playwright smoke: kiosk sign-in/out round trip, guest read-only enforcement (server responses, not UI), student-ID login, admin session edit.
- CI: lint + typecheck + tests on PR (mirroring RAR's setup), plus `supabase db` migration check.

## 8. Open questions for review

1. **Teams in v1:** the GP variant includes join modes + application queue. Fine to build, but if you want v1 even slimmer, a flat `team` list with memberships (no tree, no applications) loses little for a single FRC team — say which.
    - **Decision:** Need, including join modes + application queue
2. **Guest scope:** exactly what can a guest (parent/sponsor) see? Proposed: who's-here (names only), leaderboard, meeting schedule. Not: profiles, contact info, attendance detail.
    - **Decision:** Need · Preferred variant: proposed scope
3. **Student ID numbers:** school-issued IDs (CH's approach) or team-assigned (Den's)? Team-assigned avoids storing school identifiers; proposed default.
    - **Decision:** Need · Preferred variant: arbitrary IDs.  This let's us use phone numbers, school IDS, or any other arbitrary string as the student ID number
4. **Realtime vs poll for who's-here:** spec says Realtime with the one RLS policy; if that policy makes you uncomfortable, a 30s poll through a server route is the fallback and drops the only client-side data path.
    - **Decision:** We can just do polling for v1, and if we want to add realtime later, we can do that.  The upgrade is a nice-to-have, not a need.
